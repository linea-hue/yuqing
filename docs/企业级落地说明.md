# 电商平台企业级落地说明

## 1. 两个系统的边界

### 买家服务系统

面向买家，目标是完成交易和获得服务。只暴露本人数据和经过安全网关审查的能力：商品浏览、购物车、订单、物流、售后、文本客服和实时语音客服。

### 运营治理系统

面向客服主管、售后专员、运营、产品和安全管理员，目标是处置异常、配置规则、运营知识、评测版本和审计风险。运营人员可以提出策略变更，但不能直接绕过订单服务改写交易结果。

## 2. 企业级分层

```text
接入层：CDN/WAF/API Gateway/限流/幂等
身份层：OIDC/SSO + RBAC + ABAC + 租户/店铺/订单归属
业务域：商品、购物车、订单、履约、售后、客服、运营
智能层：意图、RAG、OCR/Evidence、Fraud、Sentiment、Decision、Voice
治理层：Critic/DLP、Tool Policy、审批、审计、评测、版本、灰度、回滚
基础设施：PostgreSQL、Redis Streams、对象存储、向量索引、Trace/Metric/Log
```

## 3. 深挖后的关键场景

| 场景 | 正常路径 | 异常/攻击路径 | 企业级处置 |
| --- | --- | --- | --- |
| 买家查询订单 | 身份校验 → 只读订单工具 → 展示物流 | 越权查询他人订单 | ABAC 订单归属校验，返回 403 并审计 |
| 购物车结算 | 价格/库存实时校验 → 生成订单 | 库存变化、重复提交、优惠叠加 | 订单服务事务、库存预占、幂等键、价格快照 |
| 低金额售后 | 证据充分 → 低风险 → 自动退款 | OCR 低置信度、政策冲突 | 补充材料或人工审批，不自动退款 |
| 高金额售后 | 决策流运行 → 挂起 → 人工审批 | 两个客服同时审批 | Redis/Lua 原子状态迁移 + 幂等键 + 版本号 |
| 恶意退款 | 历史行为 + 设备/地址特征 + 案例检索 | 伪造凭证、间接提示词注入 | Sandbox 解析、Critic 拦截、风险升级、拒绝或人工复核 |
| RAG 回答 | ACL 过滤 → 混合检索 → 重排 → 引用 | 过期政策、跨店铺知识、文档注入 | 生效时间/版本/ACL 过滤，引用校验，无证据转人工 |
| 语音客服 | VAD → STT → 意图 → RAG → TTS | 抢话、网络抖动、音频洪泛 | 取消 TTS 协程、限流、背压、断线重连、降级文本 |
| 评测发布 | Golden Dataset → 安全扫描 → 灰度 | 指标回退、裁判偏差 | 规则指标 + LLM Judge 双判定，低于阈值自动阻断和回滚 |
| 知识更新 | 草稿 → 解析 → 切片 → 审核 → 发布 | 未审核文档进入生产召回 | 状态机、双人审核、版本指针、发布前检索回归 |
| 安全事件 | 识别 → 分级 → 处置 → 复盘 | PII 泄露、工具越权、沙箱逃逸 | P0/P1/P2 分级，密钥轮换、隔离、审计和演练 |

## 4. RAG 生产化要求

1. 文档分为商品资料、平台政策、店铺政策、物流规则、售后案例、客服话术和安全规范；每类使用独立 ACL 和更新 SLA。
2. 生产索引必须保存 `tenant_id/shop_id/doc_id/version/effective_at/expire_at/acl/checksum/embedding_model`。
3. 检索前做租户、店铺、角色、商品和时间过滤，不能先召回再依赖模型自觉过滤。
4. 采用关键词 + 向量混合召回，重排后只给模型 Top 3-5 片段；文档中的指令性文字全部视为不可信数据。
5. 关键结论必须有引用 ID；没有依据、存在版本冲突或召回分低于阈值时，输出不确定性并转人工。
6. 生产环境建议采用 PostgreSQL/pgvector 起步；超过千万级 chunk 或高并发后拆分 Milvus/Elasticsearch，并保持统一检索接口。

## 5. 数据一致性与可靠性

- 订单和退款使用事务、唯一业务号、幂等键和状态版本号；Agent 不直接写交易表。
- 长任务通过 Redis Streams 投递，Worker 使用消费组、重试次数、死信队列和可观测事件。
- LangGraph Checkpointer 保存可恢复上下文；人工审批恢复时重新校验订单状态、策略版本和审批额度。
- 所有外部模型、OCR、语音服务都有超时、指数退避、熔断、降级和供应商切换策略。
- 采用 Outbox/事件表保证“业务状态变更”和“审计/消息”最终一致。

## 6. 安全基线

- 生产身份接入 OIDC/SSO，运营端按角色、店铺、金额和数据域授权。
- 高风险 Tool Calling 使用显式 JSON Schema、参数范围、订单归属、状态前置条件和二次授权。
- 沙箱只挂载限定目录，根文件系统只读，无特权、限制 CPU/内存/网络/时长，任务结束强制回收。
- 日志和 Trace 默认脱敏；密钥存 Secret Manager，严禁进入 Prompt、日志、向量库和前端响应。
- 通过 SAST、依赖扫描、容器扫描、红蓝对抗、RAG 越权测试和故障演练建立发布闸门。

## 7. 当前代码与生产差距

当前目录中的代码是“企业级架构基线 + 可运行演示”，已具备双系统入口、业务状态流、RAG 引用、安全拦截、审计事件和自动化测试。上线前必须补齐：

- PostgreSQL/pgvector 持久化和数据库迁移。
- Redis Streams Worker、Outbox、死信队列和真正的 Checkpointer。
- OIDC/SSO、RBAC/ABAC、WAF、限流和密钥管理。
- 真实 OCR、WebRTC/VAD/STT/TTS、退款支付网关和对象存储。
- Prometheus/Grafana、Langfuse、备份恢复、多副本部署和压测环境。

这些差距是生产实施项，不应通过“把演示数据写死”伪装成已经完成。
